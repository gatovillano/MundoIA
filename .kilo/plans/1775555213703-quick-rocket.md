# Integration Plan: OASIS into MundoIA Multi-Agent Simulation

## Executive Summary

**Objective**: Incorporate OASIS's scalable social simulation capabilities into MundoIA to enhance social complexity and enable scaling to millions of agents while preserving existing functionality.

**Approach**: Parallel integration - OASIS runs as an optional enhanced mode alongside the existing simulation, with a translation layer connecting both systems.

**Key Benefits**:
- Scale from ~30 to 1,000,000 agents
- 27 rich social media actions (post, comment, like, follow, repost, quote, etc.)
- Sophisticated recommendation systems (interest-based, hot-score)
- Efficient graph handling (igraph/Neo4j vs NetworkX)
- Proven async architecture for concurrent LLM calls
- Social media dynamics (feeds, viral content, echo chambers)

---

## 1. Architectural Analysis

### Current MundoIA Architecture
```
Agente (BDI + Alma + MemoriaGrafica) 
    ↓
ModeloRelacional (simulation loop)
    ↓
PostgreSQL (persistence)
    ↓
FastAPI + WebSockets → Frontend (D3.js)
```

**Strengths**: Rich agent psychology (Alma, BDI), physical world simulation, needs system, professions, institutions.

**Limitations**: 
- NetworkX doesn't scale beyond ~10k agents
- Custom action system (limited to ~15 actions)
- Simple heuristic-based content distribution
- Synchronous LLM calls limit concurrency

### OASIS Architecture
```
SocialAgent (LLM-driven) 
    ↓
Platform (async event loop) ←→ Channel (message broker)
    ↓
SQLite + igraph/Neo4j
    ↓
Recommendation Systems (recsys)
```

**Strengths**: 
- Async message-passing decouples agents from platform
- igraph handles millions of nodes efficiently
- 27 diverse actions (Twitter/Reddit style)
- Sophisticated recommendation algorithms
- Bulk operations for initialization

**Limitations**:
- Focused on social media, lacks physical world simulation
- No BDI or Alma systems
- SQLite instead of PostgreSQL

---

## 2. Integration Strategy: Hybrid Dual-Mode Architecture

### Option A: Replacement (Rejected)
Replace MundoIA's core with OASIS. **Problems**: Loses Alma, BDI, physical world, institutions, missions.

### Option B: Parallel Mode (Selected)
Run both systems simultaneously with a translation layer:

```
                      ┌─────────────────────────────────────┐
                      │   MundoIA Frontend (unchanged)      │
                      └─────────────┬───────────────────────┘
                                    │ WebSocket API
                      ┌─────────────┴───────────────────────┐
                      │    API Layer (api.py - extends)    │
                      └──────┬────────────┬─────────────────┘
                             │            │        
        ┌────────────────────▼─┐  ┌────────▼─────────────┐
        │  Traditional Mode    │  │  OASIS-Enhanced Mode│
        │  (existing)          │  │  (new)              │
        └──────────┬───────────┘  └──────────┬──────────┘
                   │                        │
            ┌──────▼────────────────────────▼──────┐
            │    Translation Layer                  │
            │  - MundoIAAgent → OASIS SocialAgent  │
            │  - OASIS Action → MundoIA Event      │
            │  - Graph sync (follow ↔ relation)    │
            │  - Profile converter                 │
            └──────┬───────────────────────────────┘
                   │
        ┌──────────▼──────────────────────────────┐
        │         OASIS Core                       │
        │  - Platform (async)                      │
        │  - AgentGraph (igraph)                   │
        │  - Recommendation System                │
        │  - SQLite database (hybrid)              │
        └──────────────────────────────────────────┘
```

### Why This Approach:
- **Backwards compatible**: Existing simulations work unchanged
- **Gradual migration**: Can migrate agents one by one
- **Feature-rich**: Keep MundoIA's Alma/BDI while gaining OASIS scalability
- **Risk mitigation**: Can fall back to traditional mode if issues arise

**Solution**: Two agent types:

1. **LLM-Driven OASIS Agents** (default OASIS behavior):

   - Good for pure social media simulation
   - Simpler to implement initially

# Modified ModeloRelacional
class ModeloRelacional:
    def __init__(self, use_oasis=False):
        self.use_oasis = use_oasis
        if use_oasis:
            self.oasis_env = create_oasis_env()
            self.oasis_agents = []
    
    async def step_oasis(self):
        """Execute OASIS step."""
        actions = {}
        for agent in self.oasis_agents:
            actions[agent] = LLMAction()  # or BDI.Action
        await self.oasis_env.step(actions)
        
    def step_legacy(self):
        """Execute traditional MundoIA step."""
        # existing logic
    
    def step(self):
        """Unified step."""
        if self.use_oasis:
            asyncio.run(self.step_oasis())
        else:
            self.step_legacy()

### Phase 4: Graph Synchronization (Week 4)
**Goal**: Keep MundoIA's relationship graph in sync with OASIS follow graph

**Why**: MundoIA uses `memoria.grafo` for relationship strength; OASIS uses `AgentGraph` for follow relationships.

**Strategy**:
- Each OASIS `follow`/`unfollow` triggers update to MundoIA's `memoria`
- MundoIA relationship changes (alliances, treaties) optionally create follow edges

```python
# graph_sync.py
class GraphSynchronizer:
    def __init__(self, modelo: ModeloRelacional, agent_graph):
        self.modelo = modelo
        self.agent_graph = agent_graph
    
    async def on_oasis_follow(self, follower_id: str, followee_id: str):
        """Handle OASIS follow action."""
        # 1. Update OASIS AgentGraph (already done)
        # 2. Update MundoIA agent's memoria
        follower = self.modelo.get_agent(follower_id)
        if follower:
            follower.memoria.registrar_interaccion(
                otro_id=followee_id,
                tipo_relacion="conocido",
                fuerza_cambio=0.1,  # Small boost
            )
    
    def on_mundo_alliance(self, agent1_id: str, agent2_id: str):
        """When MundoIA agents form alliance, optionally create follow."""
        if config.OASIS_SYNC_ALLIANCES:
            # Add bidirectional follows
            asyncio.create_task(
                self.agent_graph.add_edge(agent1_id, agent2_id)
            )
            asyncio.create_task(
                self.agent_graph.add_edge(agent2_id, agent1_id)
            )
```

**Deliverable**: Follow/unfollow actions update both graphs bidirectionally.

### Phase 6: Scalability & Performance (Week 6)
**Goal**: Achieve scaling to 10,000+ agents

**Optimizations**:

1. **Bulk Agent Initialization**:
   - Use OASIS `generate_agents_100w()` pattern
   - Batch database inserts (avoid 30× round trips)
   - Pre-generate profiles with pandas

2. **LLM Rate Limiting**:
   - OASIS uses `asyncio.Semaphore` (default 128 concurrent)
   - Reuse `cerebro_llm` rate limiter across both modes
   - Consider batching (`generar_decisiones_batch`) for efficiency

3. **Graph Performance**:
   - Switch from NetworkX to igraph (10× faster for large graphs)
   - For >100k agents, consider Neo4j backend
   - Pre-allocate graph structures

4. **Memory Management**:
   - Memoize embeddings (sentence-transformers cache)
   - Limit recommendation matrix size (`max_rec_post_len=50`)
   - Use SQLite in-memory mode for ephemeral sims

**Testing**:
- Benchmark: 100 agents → 5s per step (target)
- Benchmark: 10,000 agents → 10s per step (target)
- Memory usage < 4GB for 100k agents

**Deliverable**: Smooth simulation at 10k agents, acceptable performance.

## 5. Risks & Mitigations

| Risk | Probability | Impact | Mitigation |
|------|-------------|--------|------------|
| OASIS architecture mismatch (sync vs async) | High | Medium | Wrap async in sync for gradual migration; use `asyncio.run()` |
| LLM cost explosion (1M agents × LLM calls) | High | High | Use rule-based fallbacks; batch LLM calls; limit LLM to elite agents only |
| Memory blowup (igraph + NetworkX dual graphs) | Medium | High | Allow disabling MundoIA graph when OASIS active; use igraph for both |
| Database conflicts (PostgreSQL vs SQLite) | Medium | Medium | Use separate SQLite DB initially; sync to PostgreSQL periodically |
| LLM rate limits (OpenRouter) | High | Medium | Aggressive rate limiting; use multiple API keys; batch decisions |
| Learning curve (OASIS complexity) | High | Low | Start with minimal example; leverage OASIS Discord community |
| Performance degradation (>100k agents) | Medium | High | Benchmark early; switch to Neo4j if needed; disable tracing |
| Incompatible agent state (Alma/BDI serialization) | Low | Medium | Create migration functions; test serialization round-trips |

## 1. Análisis Arquitectural

### Arquitectura Actual de MundoIA
```
Agente (BDI + Alma + MemoriaGrafica)
    ↓
ModeloRelacional (bucle de simulación)
    ↓
PostgreSQL (persistencia)
    ↓
FastAPI + WebSockets → Frontend (D3.js)
```

**Fortalezas**: Psicología rica de agentes (Alma, BDI), simulación de mundo físico, sistema de necesidades, profesiones, instituciones.

**Limitaciones**:
- NetworkX no escala más allá de ~10k agentes
- Sistema de acciones personalizado (limitado a ~15 acciones)
- Distribución de contenido heurístico simple
- Llamadas LLM síncronas limitan la concurrencia

### Arquitectura de OASIS
```
SocialAgent (impulsado por LLM)
    ↓
Platform (bucle de eventos async) ←→ Channel (broker de mensajes)
    ↓
SQLite + igraph/Neo4j
    ↓
Sistemas de Recomendación (recsys)
```

**Fortalezas**:
- Paso de mensajes async desacopla agentes de la plataforma
- igraph maneja millones de nodos eficientemente
- 27 acciones diversas (estilo Twitter/Reddit)
- Algoritmos de recomendación sofisticados
- Operaciones masivas para inicialización

**Limitaciones**:
- Enfocado en redes sociales, carece de simulación de mundo físico
- Sin sistemas BDI o Alma
- SQLite en lugar de PostgreSQL

## 2. Estrategia de Integración: Arquitectura Híbrida Dual-Modo
